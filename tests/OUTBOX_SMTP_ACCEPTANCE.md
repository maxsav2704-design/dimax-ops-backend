# Local outbox SMTP recovery acceptance

Run from the backend directory in PowerShell, using cached reviewed image IDs:

```powershell
./scripts/test_outbox_smtp_acceptance.ps1 `
  -BackendImage sha256:f5af3ba59394a1d77dd98f74b7a57c96018d96be616e8534fcdbeaa67e335b74 `
  -PostgresImage sha256:97ff59a4e30e08d1c11bdcd9455e7832368c0572b576c9092cde2df4ae5552a3
```

The runner creates a new PostgreSQL container with `--network none`, no published
ports and PGDATA in tmpfs. The Python container shares only that network namespace.
It cannot contact production PostgreSQL, MinIO, SMTP or external recipients.
Existing services are not stopped. Source mounts are read-only; no working .env,
database volume or Docker socket is mounted. The normal application entrypoint
is bypassed. Alembic upgrades only the new synthetic `dimax_acceptance_tests` DB.
The generated test password is a fixed non-secret for this isolated namespace.
On Windows the runner now requires at least 1 GiB of free host RAM before creating
containers. Low-memory hosts must free resources first; the runner will not stop
working DIMAX services to make room. Container limits alone do not prevent host
paging or slow Docker cleanup.

Cleanup in `finally` checks the unique ownership label before deleting only the
two test containers and their anonymous volumes. No prune, application rebuild,
production migration or persisted test database is involved. A full Docker outage
or forced termination of PowerShell can interrupt cleanup; inspect the printed
container names and ownership labels before any later removal.

## Coverage

- Create a synthetic installed door and one 9.01 earnings entry, create and sign
  its journal through the actual API. Signing queues exactly one PDF email.
- Refuse a real SMTP connection: the same job remains PENDING, its attempt count
  and next scheduled time persist, and an immediate worker pass does not retry.
- Restore real STARTTLS on the same endpoint: the next eligible pass submits the
  unchanged PDF once, sets SENT and does not resend on subsequent passes.
- Exhaust the retry budget: FAILED remains stored. Restoring SMTP alone does not
  retry it. An administrator retries the same ID with an audit entry; a SENT job
  cannot be retried through that endpoint.
- Compare complete door, earnings, signature and journal-row snapshots before
  and after retries. Signed header/state/version do not change. Delivery metadata
  is expected to change and is checked separately.
- Inject a DB commit failure after SMTP acceptance to characterize the ambiguous
  delivery boundary: the job survives; a subsequent pass can duplicate the email,
  but cannot recreate the signature, installation or earnings.

PostgreSQL and SMTP transport are real. Object storage uses the suite's in-memory
fixture, and the PDF is generated by the journal service. This is not MinIO
durability, public HTTPS, external delivery or multi-worker concurrency acceptance.
The runner also includes existing retry-policy/outbox API and SMTP TLS tests.
New integration cases are opt-in and require the dedicated test environment.

## Commit-boundary correction

The real-DB failure probe found that `run_once()` previously returned one success
and emitted `outbox.message.sent` even when that message's commit had failed.
The worker now counts/logs success only after the commit succeeds, and stops the
batch after a failed commit (including failure while recording an SMTP error).
The message ID for error logging is captured before rollback to avoid reloading
an expired ORM object on a failing connection. Four additional unit cases cover
first/second commit failure, failure recording an SMTP outage, and normal batches.
Success log fields are captured before commit as well; logging must not reload
an expired ORM row after the database has already accepted the outcome.
This change does not turn SMTP into an exactly-once transport.

## Delivery semantics and remaining boundary

Current SMTP transport is **at-least-once**, not exactly-once. A remote SMTP server
can accept the email before the database commit is known to have succeeded, or
its final acknowledgement can be lost. Retrying may deliver a duplicate message.
Do not mark a job SENT before SMTP or discard it to conceal this window: that
would turn possible duplicate delivery into lost documents. SMTP submission also
does not prove delivery to the recipient's inbox.

No email retry should invoke signing, installation, price activation or accrual.
Factory links/codes must retain their existing version and authorization checks;
these journal-focused tests do not replace factory-approval acceptance tests.
The worker currently assumes a single instance; horizontal-worker safety needs
a separate claim/lease design and concurrency checks before scaling it out.

External-provider idempotency, if needed, must be evaluated when choosing the
provider. A Message-ID alone is not an exactly-once guarantee. Failed jobs require
operational review and existing audited retry controls, not manual SQL changes.
